# 执行设计：分层、职责与会话边界

本参考支撑 `foundation-initialize` 的第 3 步。先还原最小 Skill 的完整业务路径，再分别设计三种结构；三者服务于不同目的，不强制一一对应。

## 三种结构分别回答什么

- **Skill 分层**围绕可复用方法与按需读取：稳定的方法正文放在入口 Skill，体量大的领域材料拆成引用文件，执行到对应步骤才读取。
- **子智能体职责**围绕独立交付、必要隔离与能力需求：只有能独立交付、需要上下文隔离或需要不同能力的职责单元才拆出去；拆出的每个职责必须能单独验收。
- **会话边界**围绕上下文容量与阶段产物：一处会话装不下、或阶段产物需要清晰交接时才切分；切分点对应明确的阶段结果。

简单任务保留一个入口、一个会话，不为每个步骤创建 Agent；输入材料规模与已确认容量允许时，单 Skill 单会话是正常结论，并把该选择与材料规模的关系写进设计记录。

## 上下文预算方法

预算同时计入：规则与系统提示、业务输入材料、工具返回、已接受的会话历史、预计输出和余量。每一项给出依据，不以固定字数切断业务判断。

- 词元估算只能辅助判断。Foundation 已发布的确定性估算入口是 `estimateTokens`（启发式估算）与 `estimateTokenUpperBound`（UTF-8 字节上界），或 CLI `skill-family-token-estimate --file <path> --estimator both`；两者范围均为 `content-text-only`。宿主真实容量、非文本输入和模型控制开销不由它们证明。
- 宿主未提供可核验容量时，不宣称预算满足；把所缺事实和受影响的安排标为未确认，已明确的业务步骤继续梳理。
- 超出预算时按顺序处理：先减少不必要读取，再按职责拆出引用文件，然后才评估委派子智能体或新会话。

## 交接合同

每个交接职责明确：输入、必须读取的材料、允许动作、输出、人工判断标准与失败回交方式。交接携带完整必要材料与已接受结果，保留未决问题和人工决定的依据；接收方必须能从中定位业务来源、已确认结论，并知道人工判断由谁提供。不新增通用交接协议。

- 待人工确认的事项跨交接保持未决，不能被默认归入普通结论；接收方发现交接遗漏未决项时停止该部分处理，补齐后再继续。
- 宿主默认继承整段历史时，使用它已有的隔离方式，或把继承的负载如实计入预算。
- 原生 Agent 定义按目标宿主的实际合同编写；Foundation 的文本投影不把某一宿主的 Agent 文件格式转成其他宿主的配置。
- 宿主没有可用分派方式时，交付人工启动步骤，只暂停依赖自动委派的分支，其余工作继续。

## 记录位置

执行设计写入目标项目制品图登记的 Design 制品，复用该项目原有规格；目标没有制品图时，由正式 bootstrap 选择最小类型与路径。预算依据、保留或拆分各环节的理由、每处交接的内容合同都写进该记录，使后续审阅能核对决定与事实的对应关系。
